<h2>一、先分四类，别急着上自动切换</h2>
<p>故障树的根节点只问一句：现在这条连接是彻底不通，还是通着但用不了。前者往网络层走，后者往会话层走。分错方向的话，你会去重启一个本来没问题的服务，或者在一条好线路上反复切换。</p>

<h2>二、第一层：是出口侧断了，还是本地先断的</h2>
<p>这一步的判别话术是：同一时刻换一台机器、换一条网络，问题还在不在。在，就是出口侧；不在，就是本地或本机链路。很多人跳过这一步，直接换出口，结果换完还是断，白白消耗了替换额度。</p>
<h3>三条命令定位在哪一段</h3>
<p>先 ping 出口地址看链路层是否可达；再 tcping 代理端口看 TCP 能否握手；最后 curl -x 带上凭据访问一个回显地址的接口，看应用层是否通。三段里哪一段先失败，问题就在那一段之后。三条都通而业务仍失败，说明问题不在网络上，往会话层走。</p>
<h3>本地侧最常见的两个原因</h3>
<p>一是本机连接数打满，查看 ss -s 里的 TIME_WAIT 数量，几万条级别就要考虑复用连接或缩短回收时间；二是本地网络在后台切换，笔记本从无线切到有线、手机从蜂窝切到无线，出口地址跟着变，长连接自然断。这类断线不需要改代理配置，加一条网络变更时的重连逻辑就够。</p>

<h2>三、第二层：连得上但用不了，通常是会话问题</h2>
<p>这一层的特征是握手成功、返回很快，但业务侧报错。判别话术是：把同一个请求原样重发一次，结果是否一致。稳定复现就是配置或凭据问题，时好时坏才可能是线路或限流。</p>
<h3>407、403、429 分别指向不同位置</h3>
<p>407 是代理鉴权没过，多出现在白名单变更、凭据过期、或者源地址漂移之后。403 来自目标站点，通常与访问内容或账号状态有关，与代理本身关系不大。429 是限流，先看自己的并发曲线，再看供应商是否对单出口设了请求上限。三种码不要用同一套重试策略，407 重试没有意义。</p>
<h3>会话粘性掉了会表现成什么样</h3>
<p>如果业务依赖同一出口连续访问，而代理侧把请求分到了不同节点，日志里会出现"几分钟内出口地址跳了三次"。这种不是断线，是调度问题。处置办法是在请求里带上会话标识，或者直接换成静态出口，比反复重连有效。</p>

<h2>四、第三层：主备切换为什么没触发</h2>
<p>配了备用线路却还是断了十几分钟，问题多半在判定条件上。常见三种：探测频率太低，等发现时业务已经报错一片；判定条件太严，要连续失败十次才切，实际早就超时；探测目标只有一个域名，那个域名本身在抖动，导致切换判断失真。</p>
<h3>把探测做成两个目标、两种协议</h3>
<p>一个目标用 HTTP 请求回显地址接口，另一个用 TCP 握手探测代理端口。两个都失败才认定出口不可用，单个失败只记一次告警。探测间隔 15 秒，连续 3 次失败触发切换，这个组合在实践中比较平衡。切换动作要幂等，重复触发不会把配置改乱。</p>
<h3>切换之后要验证出口真的变了</h3>
<p>切换脚本里加一步：切完立刻请求回显接口，比对返回地址是否等于备用出口。没有这一步，很容易出现"配置改了、连接还挂在旧通道上"的情况，看起来切了其实没切。</p>

<h2>五、告警怎么配才不吵人</h2>
<p>告警的目标是让人在需要动手时被叫醒，而不是把所有波动都推一遍。按影响面分级，比按技术指标分级更贴近实际。</p>
<h3>三级就够，别做五级</h3>
<p>一级是业务不可用，立即电话或即时消息；二级是可用但质量下降，工作时间推送；三级是单次探测失败，只进日志和日报。分级之后，误报带来的疲劳会明显下降，真正的问题也更愿意被及时处理。</p>
<h3>把恢复也发一条</h3>
<p>只发故障不发恢复，值班的人不知道现在还要不要看。恢复通知里带上持续时间、切换次数、当时的出口地址，事后复盘直接能用。</p>

<h2>常见问答</h2>
<h3>断线后自动重连会不会被当成异常行为？</h3>
<p>答：正常的网络重连属于常规现象，不必过度担心。需要注意的是重连频率和地址变化幅度，如果一分钟内换了好几个地址，建议先修线路，而不是继续加重连次数。</p>
<h3>备用线路平时要不要一直挂着？</h3>
<p>答：建议保持低频探测但不承载业务。完全冷备时，真出事才发现备用线路本身也有问题；一直承载业务又会分摊流量、增加成本。折中做法是每天切一小段流量过去验证。</p>
<h3>怎么判断是供应商的问题还是自己的问题？</h3>
<p>答：用一台与你环境无关的机器，通过同一出口做同样的请求。它能通而你这边不通，问题偏本地；两边都不通，再去找供应商，沟通时附上时间点、出口地址和错误码，处理会快很多。</p>
<h3>监控要不要直接探测 Claude 的接口？</h3>
<p>答：低频探测可以，但不要用真实业务凭据，也不要用高频请求。更稳妥的是探测回显地址接口加一个通用 HTTPS 站点，既能反映线路质量，又不会给业务侧带来额外负担。</p>
